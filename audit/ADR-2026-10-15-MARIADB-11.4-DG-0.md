# ADR-2026-10-15 — MariaDB 11.4 LTS for Central and Tenant Databases

**Status:** PROPOSED FOR REVIEW — DG-0 is not accepted until a reviewer approves this ADR and source inventory.  
**Date:** 2026-10-15  
**Decision owner:** Repository architecture review  
**Scope:** Target engine selection for the Laravel/KVM2 migration; no live database is modified.

## Context

Root `AGENTS.md` Section 3 specifies MariaDB 11.4 LTS unless a reviewed ADR replaces it. The intended topology is one private MariaDB server holding `berkahpos_central` plus a separate database and restricted database user for each tenant. The Laravel application uses PDO MySQL/MariaDB configuration and `stancl/tenancy`'s MySQL database manager. Compose and CI are therefore changed to use explicit `mariadb:11.4` image tags instead of the mutable major-only `mariadb:11` tag.

The archived legacy source is PostgreSQL/Supabase-oriented. The sanitized source-level inventory is in `audit/DG-0-SUPABASE-SCHEMA-INVENTORY-2026-10-15.md`. It identifies JSONB, PL/pgSQL functions/RPCs, Supabase JWT helpers and RLS dependencies that cannot be copied directly into MariaDB. This ADR makes no claim that live Supabase schema, data, grants, extensions or hosted resources were inspected.

## Decision proposed

Select **MariaDB 11.4 LTS** for target central and per-tenant databases on the same private database server. Do not treat PostgreSQL 17 or hosted Supabase as the active runtime data plane for this target. Retain old PostgreSQL SQL/migration/test files only in `docs/archive/supabase-historical/`; never run them in active Laravel CI, deployment or runtime.

This is a repository architecture proposal awaiting review; it is not evidence of a running MariaDB 11.4 server or completed data migration.

## Alternatives considered

| Option | Advantages | Costs / reasons not selected |
|---|---|---|
| MariaDB 11.4 LTS | Matches root AGENTS target; matches PDO MySQL and the tenancy MySQL database manager; supports central plus separate tenant databases on one private server; permits one application service and per-tenant DB/grant boundaries. | PostgreSQL JSONB/PLpgSQL/RLS/Supabase identity behavior must be reimplemented and tested; database-level RLS protection is not automatically carried over. |
| PostgreSQL 17 | Closer source compatibility with legacy JSONB, PL/pgSQL, pgTAP and Supabase function/RLS artifacts. | Conflicts with current target-engine directive and requires changes to database configuration, provisioning manager, operational topology and acceptance tests; it does not by itself reproduce the desired Laravel tenant provisioning model. |
| Keep hosted Supabase as active runtime | Least immediate SQL porting for existing RPC/RLS paths. | Conflicts with target platform and database-per-tenant decision; keeps hosted runtime/auth/RLS as an operational dependency rather than completing the migration. |

## Migration cost assessment

The cost assessment is qualitative, not a time/currency estimate.

- **High — authorization and isolation:** translate RLS + `auth.uid()`/`auth.jwt()`/service-role checks to Laravel/Sanctum and real MariaDB grants; run adversarial Tenant A/B tests.
- **High — RPC semantics:** reimplement `get_effective_config` and `update_app_config_atomic` while preserving five-layer ordering, service isolation, row-level authorization, optimistic version check, row locking, version bump, transaction behavior and conflict handling.
- **High — data ownership:** move legacy shared-schema projections to central metadata plus distinct tenant DBs without fabricating historical records or losing tenant/device ownership.
- **Medium/high — configuration JSON:** map JSONB operators to MariaDB JSON features or normalized columns and prove canonical 352-key/effective-config parity.
- **Medium — tests and operations:** replace pgTAP with executable PHPUnit/integration tests against disposable MariaDB; add per-tenant backup/restore, grants, idempotent provisioning and migration rollback evidence.
- **Unknown — hosted source/data migration:** live row counts, actual extensions/functions/policies, data volume, external dependencies, retention obligations and transformation exceptions are NOT VERIFIED; therefore no honest time/cost estimate can be given yet.

## Required acceptance gates

1. Reviewer accepts this ADR and sanitized source inventory.
2. Obtain a current, authorized read-only PostgreSQL/Supabase schema/function/extension/RLS/grant inventory and export/backup checksums before any source-data migration.
3. Demonstrate clean MariaDB 11.4 startup, central migrations and two separate tenant DBs/users in a disposable environment.
4. Prove database accounts cannot access other tenants' DBs and normal web/queue app processes do not receive provisioning/root credentials.
5. Replace PostgreSQL-specific RPC/RLS behaviors with Laravel/database equivalents and run effective-config, transaction, authorization and idempotency tests.
6. Execute central-plus-tenant backup/restore, including single-tenant restore, before production cutover.
7. Keep historical Supabase SQL outside active migration paths and prove workflows/deployments do not execute it.

## Security and evidence boundary

No credentials, connection URLs/tokens, production rows or hard-coded secrets are included in this ADR. No live database was connected, no production migration was run, and no backup/restore was executed in this task. DG-0 remains **NOT VERIFIED for live environment state** until the catalog/export and disposable-engine gates above are complete.
